Overhaul missions inside Fizzer.

Outcome. Deliver a first, real mission slice where a person and the orchestrator can shape a plan, dispatch bounded research and implementation work, review the resulting code, integrate it, and verify the delivered Fizzer mission-overhaul changes together. Narrative is a later project, outside this mission. The mission workspace is the primary interface; the right-hand channel supports it.

Agreed UX and operating model

  • Missions are first-class vault workspaces with a durable identity, dedicated channel, root/brief association, and one explicit lifecycle: planning → execution → closed.
  • The Brief and Work views share editable mission, milestone, and feature notes. Open questions stay visible at every level; history, details, worker inspection, trace/fullscreen, and steering remain on demand.
  • The orchestrator keeps intent, dependencies, decisions, assignments, and follow-through coherent. It gives positive operating instructions; it does not enforce a new role/tool-ban system.
  • Workers are explicitly assigned separate research, implementation, review, and integration tasks. @worker navigation is inspection, not assignment.
  • Human edits are inputs to planning. A note save is not worker steering; steering is an explicit action and worker output prompts orchestrator follow-through.

Clean replacement decision

This is one replacement mission system, not a legacy/new split. Replace the mission model, lifecycle, execution path, callers, helpers, prompts, UI wiring, and tests from the ground up; migrate every current mission caller to the new contract and remove obsolete mission code, comments, compatibility shims, experience-version branches, nullable legacy phases, and old-behavior regression coverage. Reuse generic vault, note, chat, task, outbox, scheduler, runner, and event infrastructure only where its verified contract fits; that reuse does not preserve old mission execution. Acceptance includes evidence that no old mission execution path remains.

Historical records

Existing mission records are not silently deleted. Baseline work must inventory their shape and count, choose and document a one-time migration mapping into the replacement schema or explicit read-only retention outside the runtime, record unmigrated/failed records and audit outcomes, and complete that decision before cutover. Historical retention is distinct from keeping a legacy runtime: the shipped system has one replacement lifecycle and no fallback reader or executor.

Evidence and current gap

Earlier Factory/code research and the user-approved mockup established useful role separation, milestone planning, visible state, and mission-central navigation. Those are recorded as prior evidence, not a fresh source recheck. The existing Fizzer scheduler/outbox/run events/chat/notes/work-item review are generic integration foundations to verify against the post-#5–#10 contracts, not mission behavior to preserve. The gap is the end-to-end replacement mission identity, planning behavior, shared-note awareness, positive dispatch/follow-through, and real data/event wiring that turns those foundations into a usable mission workflow inside Fizzer.

Sequence and boundaries

  1. Verify the current integration baseline, inventory historical mission records, settle their one-time migration or read-only retention decision, and approve this scope against #5–#10.
  2. Build the replacement mission identity/schema and planning storage/discovery, then safe shared notes and replacement orchestrator lifecycle behavior.
  3. Freeze contracts before parallelizing the Mission Control frontend with runtime work in separate files; migrate all callers/helpers/prompts and remove superseded mission implementation as each seam lands.
  4. Exercise the full create → edit/clarify → research → approve → implementation → review/fix → integration → verification → closed loop, including reconnect, history, and steering cases, and prove no old execution path remains.

Non-goals: a giant framework, invented worker activity, fabricated elapsed/usage data, tool enforcement, a research-only cutoff, a disconnected mock control surface, or a compatibility runtime for old missions. This HTML remains a local/in-memory prototype until production wiring lands.

Open questions

Which current #5–#10 contract details need correction during baseline verification, which historical-record migration or retention mapping is safest, and which remaining overhaul task can exercise the replacement mission workflow once it is usable?

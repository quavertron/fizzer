# Exact scoped execution recovery

Operators may install `execution-admission.json` in `CASCADE_DATA_DIR` **before** a normal release/restart. It is read once by runtime configuration, before scheduler/transport startup. Invalid/unreadable content aborts startup; absence means the established unrestricted application policy. Preserve the file across releases; deleting it and restarting explicitly ends the scope. No schema, historical task status, permission or notification reset is performed.

Shape: `{ "version": 1, "owners": [{ "ownerId": 123, "maxConcurrent": 2, "tasks": [...], "retainedRuns": [], "instructions": "Optional narrowing constraints; never additional authority" }] }`.

Each task entry binds exact `taskId`, `missionId`, `workItemId`, `registrationId`, `identityId`, `ownerId`, `vaultId`, `channelId`, `attempt`, `dispatchId`. An existing dispatch must be supplied exactly. Null dispatch permits native scheduling of that exact task only, not any other task or coordinator wake. Optional `requireRepository` keeps execution held until the explicit repository-only recovery operation has bound the expected repository. Task owner, work-item owner/source, vault/channel, identity owner, current attempt, current dispatch/task link and unchanged yolo=false are rechecked. New task IDs/attempts require a fresh explicitly authorized policy. There is no creation-time/date heuristic or implicit descendant grant.

Admission covers scheduler selection/coordinator wakes, pending outbox selection, all pending execution checks, final serialized immediate-transaction claim, initial delegation, lifecycle replay and existing transport enqueue/drain authorization. `maxConcurrent` accepts `1`, `2`, or the explicit string `"unlimited"`. Finite limits count all queued/running claims per scoped owner across agents and channels; they never cancel already running jobs. `"unlimited"` removes only this owner-wide capacity cap, not exact source/task/workflow admission, qualification budgets, Stop, session ownership, permissions, or provider limits. Missing/null/malformed values fail closed; they do not silently mean unlimited. Retained authorized work uses exact `{runId,vaultId,dispatchId}` entries, not timestamps or all active IDs by default. Unscoped owners retain established behavior. A packet already handed to a real runner cannot be recalled by this policy; inspect the global read-only baseline before activation. Scoped owners' unlisted new chat dispatches also remain held until explicitly admitted. Do not describe this recovery mode as ordinary always-on scheduling.

Authenticated SELECT-only `GET /api/execution-admission-v1` reports the current account's loaded policy. Independently compare it with the intended exact file **before** desktop reconnect. Do not confuse a file write or deployed source with activated admission.

`GET /api/work-items/:id/repository-binding-v1` returns a SELECT-only exact chain/item/execution preview and revision. `PUT` accepts only `{repository,expectedRevision}`. An immediate transaction revalidates ownership, exact pending task and dispatch, absent run/lease/worktree/base/repository, yolo=false and the complete preview before changing only repository. No direct run/retry or permission mutation. The Along named `updateWorkItem` repository-only action negotiates this contract and retains private exact-preview grants plus durable no-replay receipts. Filesystem/Git validation occurs on the owner's desktop; the backend does not inspect its own unrelated filesystem as the user's source repository.

Workspace preparation preserves exact parent source ownership/vault/channel/mission and inherits one completed dependency worktree for sequential stages; divergent dependency worktrees refuse rather than choosing a query-order branch. Real desktop worktree preparation owns Git validation and work-item binding. No global cwd or dirty-root edit is implied by supplying a source repository.

Verification includes actual missing-repository failure -> guarded bind -> native websocket workspace request -> real Node worktrees module on disposable Git -> same original dispatch/one run and exact isolated cwd, with an inert runner and no model invocation. Disconnected/reconnected old dispatch plus queued transport refusal leaves run/dispatch state and delivery attempts unchanged; exact retained work remains deliverable. Existing no-invoke message and transport-revocation suites remain release gates.
